# 真机基准计划

## 目的

基准用于区分 HTML/AST 解析、React reconciliation、原生或 DOM 布局、媒体请求和图片/SVG 解码的成本，并比较 RNRH、单 DOM/WebView 与虚拟化 Block renderer。所有正式对比都在 release 构建完成，开发模式结果只用于定位问题。

## 测试矩阵

至少覆盖：

| 类型 | 主要压力 | 当前样本 |
| --- | --- | --- |
| 短文本 | 普通段落、链接 | 待补充 |
| 公式密集 | 远程 SVG、行内布局 | `article-formula-heavy-001` |
| 图片/视频 | 图片尺寸、解码、媒体卡片 | 待补充 |
| 长图混合内容 | 大量图片、媒体、链接 | `long-image-heavy-001` |
| 真正超长文本 | 大量段落、列表、引用、inline run | 待补充，现有 `pig.json` 不能替代 |
| 非法/异常 HTML | 清洗、fallback、深层嵌套 | 待补充 |

每类内容至少在一台 Android 和一台 iOS 真机运行。记录设备、系统版本、构建 commit、网络条件与冷/热缓存状态。

## 关键时间点

- `content_received`：API 数据进入页面组件。
- `renderer_start`：正文渲染器开始处理内容。
- `first_content_layout`：首段或首个可见 block 完成布局。
- `content_layout_stable`：首屏内媒体尺寸稳定，不再发生明显跳动。
- `interactive`：图片、链接、文本选择等交互可响应。

## 指标

- 数据可用到首段布局的耗时。
- 首屏布局稳定耗时及布局次数。
- 连续滚动时 JS/UI 掉帧与长任务。
- 峰值内存及退出页面后的回收情况。
- 正文图片、公式 SVG、KaTeX/CSS/字体请求数。
- WebView bridge 消息数量和正文树/TTree 重建次数。
- 当前挂载 block/View 数量，以及离屏 cell 回收情况。

## 正确性矩阵

性能更快但内容排错、交互丢失，不视为可替换方案。每个 renderer 都要检查：

| 能力 | 验收重点 |
| --- | --- |
| 行内公式 | `eeimg=1` 与相邻文字同一行，baseline、行高和换行稳定 |
| 块级公式 | `eeimg=2` 居中、缩放与横向溢出行为明确 |
| 知识点片段 | Android/iOS 的线型、颜色、点击范围与文本选择 |
| 图片/视频/卡片 | 尺寸稳定、点击/长按、链接和 fallback |
| 排版 | 段落、列表、引用、代码、粗斜体、暗色模式和字号缩放 |
| 安全 | 脚本、事件属性、危险 URL 和非法 bridge 消息被拒绝 |

## 对比规则

- 同一设备、同一内容、同一构建模式至少运行 5 次。
- 冷缓存和热缓存分开记录，不混合取平均值。
- PR 附原始记录和中位数/P95；不只提供主观录屏。
- 视觉和交互回归与性能结果同等重要。
- WebView 方案按“一页最多一个、内部滚动”测试，不用每段/每公式 WebView，也不以自动增高桥接作为最终结构。
- Block 方案必须证明只挂载可见窗口附近的 block；否则不能声称解决了超长正文问题。

完整架构和分阶段验收见 [Renderer V2 迁移计划](./renderer-v2-plan.md)。
