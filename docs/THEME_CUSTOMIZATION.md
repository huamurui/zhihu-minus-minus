# 文字与背景主题调整方案

本文只讨论应用自身的文字、背景和表面层颜色，不包括知乎接口返回的标签色、作者头像等内容数据。当前目标是先明确可调整的层级和用户体验，再决定具体色值与实现范围。

## 当前状态

目前已经具备：

- `system / light / dark` 三种主题模式；
- 用户自定义主色；
- 字体大小和行高比例调整；
- 阅读背景、文字对比度和表面层次的低门槛选项；
- light/dark 的静态颜色 token；
- NativeWind、React Native、React Navigation 共用主题来源；
- 运行时主题解析器，会根据这些偏好生成当前语义颜色。

目前还没有：

- 用户对正文文字颜色的直接调整；
- 用户对阅读背景颜色的直接调整；
- 自定义颜色之间的对比度校验；
- 富文本 WebView 与原生富文本完全共用运行时文字/背景变量。

当前试验版本已经在“外观与定制”中接入以下三个选项：

- 阅读背景：默认、柔和、暖色、低亮；
- 文字对比度：标准、高对比；
- 表面层次：分层、扁平。

它们只覆盖应用自己的语义颜色，不会修改知乎接口提供的内容颜色。部分历史组件仍直接读取静态 `Colors[colorScheme]`，这些组件不会立即响应新的阅读背景或对比度偏好，后续需要继续迁移到运行时主题 hook。

因此，文字和背景调整不建议直接开放一组几十项 HEX 输入。这样虽然自由度高，但容易造成文字不可读、卡片层级混乱，以及设置页面本身难以理解。

## 建议的三层能力

### 第一层：主题预设

给大多数用户提供少量完整方案，每个方案同时定义 light/dark 下的：

- 页面画布色；
- 卡片和浮层色；
- 正文、次要文字、弱化文字；
- 边框和分割线；
- 链接色和按钮主色。

预设可以先考虑：

| 方案 | 适合场景 | 特点 |
| --- | --- | --- |
| 默认蓝 | 普通使用 | 保留当前品牌蓝和现有层级 |
| 阅读柔和 | 长时间阅读 | 降低纯白、纯黑和边框刺激 |
| 高对比 | 可读性优先 | 正文和次要文字对比度更高 |
| 暖色阅读 | 夜间或护眼偏好 | 背景略偏暖，减少冷白感 |

预设应该是完整的语义主题，而不是只替换一个背景色。否则会出现按钮、链接、反色文字与新背景不匹配的问题。

### 第二层：低门槛调节

推荐优先提供开关、单选或少量滑杆，而不是要求用户理解颜色 token：

1. **阅读背景**：默认、柔和灰、暖白、深色；
2. **文字对比度**：标准、高对比；
3. **表面层次**：扁平、分层；
4. **阅读密度**：沿用现有字体大小和行高设置；
5. **主色**：沿用已有预设和自定义颜色。

这组控制可以覆盖大多数“白底太刺眼”“灰字看不清”“卡片层次不明显”的诉求，同时不会让用户逐项调坏界面。

建议的设置模型可以是：

```ts
interface ThemePreferences {
  mode: 'system' | 'light' | 'dark';
  primaryColor: string | null;
  readingBackground: 'default' | 'soft' | 'warm' | 'dim';
  textContrast: 'standard' | 'high';
  surfaceStyle: 'flat' | 'layered';
}
```

其中 `readingBackground`、`textContrast` 和 `surfaceStyle` 应该覆盖语义 token，不应直接修改组件样式。

### 第三层：高级自定义

如果后续确实需要更高自由度，可以允许用户调整以下少量角色：

- 阅读背景；
- 正文文字；
- 次要文字；
- 链接/强调色。

不建议让用户分别调整每个页面、卡片、按钮和图标。高级自定义至少需要：

- 实时预览；
- 一键恢复当前主题默认值；
- 颜色格式校验；
- 正文与背景对比度提示；
- 主色背景上的 `onPrimary` 文字颜色自动选择；
- 对比度过低时禁止保存，或自动修正并说明原因。

任意颜色都不能保证在所有场景下同时满足可读性，因此高级模式必须把对比度作为约束，而不是只提供颜色选择器。

## 推荐的 token 结构

建议将颜色分为三层：

```text
基础色值 primitives
  ↓
语义角色 semantic roles
  ↓
运行时用户覆盖 runtime overrides
```

组件只依赖语义角色，例如：

```ts
interface ThemeColors {
  canvas: string;
  surface: string;
  surfaceElevated: string;
  textPrimary: string;
  textSecondary: string;
  textMuted: string;
  borderSubtle: string;
  divider: string;
  actionPrimary: string;
  onPrimary: string;
  link: string;
  scrim: string;
}
```

运行时主题可以由以下输入解析：

```ts
createThemeColors({
  mode,
  preset,
  primaryColor,
  readingBackground,
  textContrast,
  surfaceStyle,
});
```

这样用户调整的是“阅读背景”或“文字对比度”，而不是让页面组件知道某个具体 HEX 值。

## 需要特别处理的场景

### 富文本

原生富文本、`react-native-render-html` 和 WebView 当前存在不同的颜色入口。后续应让它们都接收解析后的语义颜色，至少统一：

- 正文文字；
- 次要文字；
- 页面背景；
- 链接；
- 引用块背景和边框；
- 代码块背景。

否则用户调整阅读背景后，正文区域可能变了，但引用块、公式或 WebView 内容仍然使用旧颜色。

### 主色与文字颜色

主色不应继续同时承担品牌色、链接色、按钮背景和按钮文字背景。至少需要区分：

- `actionPrimary`：按钮、选中态和交互控件；
- `link`：正文中的链接；
- `onPrimary`：主色背景上的文字和图标。

自定义主色变化后，`onPrimary` 应根据亮度自动选择，而不是固定使用 `textInverse`。

### 兼容和迁移

已有用户只设置了主色，因此新增文字/背景偏好时应：

- 默认保持当前视觉；
- 新字段使用 `null` 或明确的默认枚举值；
- 不覆盖已有的主色、字体大小、行高设置；
- 对非法或过期的颜色组合回退到安全预设。

## 推荐落地顺序

1. 抽取 `createThemeColors`，让静态 token 和运行时偏好走同一个解析入口；
2. 增加“阅读背景”和“文字对比度”两个低门槛设置；
3. 给设置页增加小型预览卡片，实时展示正文、次要文字、链接、引用块和按钮；
4. 将富文本各渲染路径改为接收解析后的语义颜色；
5. 最后再考虑高级颜色输入，并加入对比度约束。

当前试验实现先做第二层能力。它能解决用户最常见的阅读感受问题，同时保留预设主题的稳定性，也不会把 token 系统重新变成一堆组件级颜色配置。下一步再处理历史静态颜色入口和富文本 WebView 的完整同步，最后才考虑带对比度约束的高级颜色输入。
